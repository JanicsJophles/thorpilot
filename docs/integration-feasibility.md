# Integration feasibility and evidence

Checked 2026-10-07. **Documented** means a primary source describes the feature. **Source-observed** means current upstream implementation contains a mechanism; it is not a stable API promise. **Proposed** means Thorpilot has not implemented and verified the integration. Device testing must record exact package/version and Android build, without publishing personal device identifiers.

| Integration | Evidence | First useful Thorpilot integration | Limit and proof still needed |
| --- | --- | --- | --- |
| Cocoon widget | Documented: installed Android app widgets can be placed on Home. [Cocoon widgets](https://cocoon-shell.com/wiki/widgets/) | Proposed Android widget opening conversation or request status. | Verify host resizing, controller focus, launch display, refresh behavior. No third-party Pod SDK was established by [Pod documentation](https://cocoon-shell.com/wiki/pods/). |
| Cocoon display routing | Documented per-app, per-game and folder display choices. [Dual-screen guide](https://cocoon-shell.com/wiki/dual-screen/) | Let users choose Thorpilot's launch display through Cocoon. | No verified programmatic route to rewrite Cocoon choices. Test reverse roles, app return, and docking. |
| Cocoon library setup | Documented platform players, per-game overrides, manual rescan, and M3U grouping. [Emulator setup](https://cocoon-shell.com/wiki/emulator-setup/) | Guided setup and explicit “rescan next” instruction after transfers. | No external rescan/launch/export API verified. [Backup UI](https://cocoon-shell.com/wiki/backup-and-restore/) is not a machine API or permission to edit internal databases. |
| Android storage | Documented user-selected document/tree grants and provider capabilities. [Storage Access Framework](https://developer.android.com/training/data-storage/shared/documents-files) | Proposed inventory and verified transfers inside a chosen ROM folder. | Grants can disappear after moves/deletion; Android 11+ restricts roots and Android/data/obb. An SD card's desktop path is not its Android URI. |
| Android display | Documented `Presentation` lifecycle and display removal behavior. [Presentation](https://developer.android.com/reference/android/app/Presentation) | Current native secondary presentation; strengthen recovery and handoff tests. | A presentation is not permission to control other apps or their screens. Use its display-specific context and handle rejected/removed displays. |
| Android accessibility | Documented optional window-content and gesture capabilities. [Accessibility service guide](https://developer.android.com/guide/topics/ui/accessibility/service) | Proposed, opt-in guided task adapter only if documented APIs cannot finish a task. | Separate disclosure, user enablement, narrow package scope, visible execution and stop control. Custom-rendered emulator views may expose little useful structure. No general control guarantee. |
| Azahar | Source-observed exported `EmulationActivity` accepts content VIEW intents; implementation also uses internal game objects. [Manifest](https://github.com/azahar-emu/azahar/blob/master/src/android/app/src/main/AndroidManifest.xml), [activity](https://github.com/azahar-emu/azahar/blob/master/src/android/app/src/main/java/org/citra/citra_emu/activities/EmulationActivity.kt) | Launch the installed app first; prototype one version-pinned game launch with a user-granted URI. | Manifest inspection alone does not prove a complete launch contract. CIA installation, saves, layouts and config access need separate verification; no silent installation or universal config API claimed. |
| melonDS Android | Documented frontend package/activity, preferred ROM URI with read grant, and prior scan/save-location caveat. [Upstream README](https://github.com/rafaelvcaetano/melonDS-android/blob/master/README.md#integration-with-third-party-frontends) | Proposed explicit launch of an already-scanned ROM; inspect a selected save directory. | This upstream uses `me.magnum.melonds`. melonDualDS and other forks must get separate manifests/version tests. Do not assume identical private settings or save paths. |
| PPSSPP | Documented user-selected PSP memory-stick folder. [Android storage](https://www.ppsspp.org/docs/getting-started/save-data-and-storage/). Source-observed VIEW file/content filters. [Manifest](https://github.com/hrydgard/ppsspp/blob/master/android/AndroidManifest.xml) | Proposed save backup through a separately granted directory; version-tested game launch. | Choosing a folder in PPSSPP does not grant Thorpilot access. Renaming the PSP folder can change its interpretation. Configuration editing/telemetry needs a dedicated adapter. |
| RetroArch | Documented separate configuration, core options, remap and shader override systems. [Overrides guide](https://docs.libretro.com/guides/overrides/). Source-observed ROM/LIBRETRO intent extras. [Android activity](https://github.com/libretro/RetroArch/blob/master/pkg/android/phoenix/src/com/retroarch/browser/retroactivity/RetroActivityFuture.java) | Proposed backup and preview of one game override in an accessible directory; later verified launch. | Core identity, precedence, package variant and writable location matter. Do not overwrite global configuration or treat all core options as equivalent. |
| Thermal context | Documented Android thermal status API. [PowerManager](https://developer.android.com/reference/android/os/PowerManager#getCurrentThermalStatus()) | Proposed visible thermal-state context during experiments. | Thermal state is not game FPS, per-process power, or precise CPU/GPU temperature. Unknown telemetry stays unknown. |
| ROMarr | Current custom requests/chat contract is documented in [chat adapter](chat-adapter.md). | Existing discovery chat and read-only request view. | Capability negotiation and stock-server compatibility are proposed. A connected request server is not universal emulator control. |

## Adapter acceptance record

For every supported adapter, record: upstream source revision, app package and version range, accepted input URI/format, required grants, expected foreground/display behavior, supported actions, failure states, rollback strategy, and dated physical-device evidence. A failed or unknown version match disables mutating actions while retaining guidance.

Before declaring an emulator “supported,” demonstrate a user-visible round trip: choose a known test fixture, preview the action, launch or apply it, observe the expected result, return to the companion, and restore any changed state. Use redistributable homebrew/test content in public fixtures.
